# TimescaleDB backup and restore

pgBackRest, backing up to the existing MinIO deployment (`k8s/minio`). See
the project chat log / `restaurant-platform-implementation-status.md` for
the full reasoning; this file is the quick reference.

## Why pgBackRest

- It is already installed in the `timescale/timescaledb-ha` image this
  project uses (`pgbackrest version` inside the pod works today, before any
  of this chart is applied) -- no new image, no new dependency.
- It supports continuous WAL archiving (point-in-time recovery -- restore to
  *any* moment, not just to when a backup happened to run) alongside full
  and differential backups, which a plain `pg_dump` cron cannot do.
- It talks S3-compatible object storage natively, so it backs up straight
  to the MinIO this project already runs (previously idle) instead of
  requiring a new storage target. Note: pgBackRest's S3 driver always
  speaks HTTPS (there's no plain-HTTP mode -- `repo1-storage-verify-tls`
  only skips certificate *validation*, not encryption), so MinIO now runs
  with a self-signed TLS cert (`k8s/minio/values.yaml`'s `tls.secretName`,
  generated by `harden-live-cluster.sh`) purely to satisfy this.

Alternatives considered: WAL-G (similar, lighter, also solid -- pgBackRest
was picked mainly because it was already sitting in the image); a plain
`pg_dump`/`pg_dumpall` cron (simpler to understand, but no PITR and no
incremental/differential backups, so a restore always replays the whole
database from the last dump); a Postgres operator such as CloudNativePG or
the Zalando one (would bring backup/restore and HA together, but replaces
the hand-rolled StatefulSet this project deliberately built instead of
depending on one, per its own stated priority of showing storage depth
rather than adopting an operator); Velero (snapshots PVs and cluster
objects generically, but has no idea what a WAL segment is -- fine for
whole-namespace disaster recovery, not for point-in-time database restore).

## Layout

- `templates/pgbackrest-configmap.yaml` -- `pgbackrest.conf`, mounted into
  the `timescaledb` pod itself (fixed name, same cross-chart pattern as
  `k8s/phase5-schemas`). The two S3 credentials are deliberately not in this
  file; they come from the `PGBACKREST_REPO1_S3_KEY(_SECRET)` environment
  variables instead (a documented pgBackRest mechanism), sourced from the
  `pgbackrest-minio-credentials` Secret.
- `templates/rbac.yaml` -- a ServiceAccount and Role scoped to
  `pods/exec` on exactly `timescaledb-0`, nothing else.
- `templates/cronjobs.yaml` -- two CronJobs (full weekly, differential
  daily) that `kubectl exec` into `timescaledb-0` to run `pgbackrest backup`.
  Continuous WAL archiving happens on its own via `archive_command`; these
  are only for the periodic full/diff backups pgBackRest itself does not
  trigger automatically.
- `templates/restore-drill-job.yaml` -- **not** installed by `helm install`
  (no hook). Applied on demand by `restore-drill.sh`.

## One-time setup

```bash
bash k8s/harden/harden-live-cluster.sh --dry-run   # read every step first
bash k8s/harden/harden-live-cluster.sh
```

This also rotates TimescaleDB/narrator/MinIO passwords and turns on the
dashboard/game-bridge API keys -- see that script's own header for why
these are bundled together. It creates the bucket, a MinIO user scoped to
only that bucket, turns on WAL archiving, creates the pgBackRest stanza,
and takes the first full backup.

## Prove it actually restores

```bash
bash k8s/timescaledb-backup/restore-drill.sh
```

Restores the latest backup into a scratch pod (a throwaway `emptyDir`,
never the real `data-timescaledb-0` PVC), starts Postgres against it on an
alternate port, prints row counts and the newest timestamp per table, then
deletes the scratch pod. If the counts and timestamp look like the real
database, the backup is real.

**Verified end to end against the live cluster** (2026-09-24): a full backup
was taken, and `restore-drill.sh` restored it into a scratch pod and printed
real row counts and `max(timestamp)` values pulled from the restored copy,
not the live database. Three real bugs surfaced and were fixed along the
way, each worth knowing about since they'll resurface in any similar setup:

1. **MinIO is a StatefulSet with no restart-on-secret-change wiring** --
   rotating its root password updated the Secret but left the running pod
   on the old one (only reads env vars at container start), so the
   bucket-init hook Job got a "signature does not match" auth error talking
   to a MinIO that hadn't restarted yet. Fixed with a `checksum/secret`
   pod-template annotation (`k8s/minio/templates/statefulset.yaml`) so a
   password change forces a real rollout as part of the same `helm upgrade`.
2. **pgBackRest defaults to connecting as role `postgres`**, which doesn't
   exist here -- the official Postgres image only creates the role named by
   `POSTGRES_USER` (`restaurant_app`) at initdb time. Needed `pg1-user`
   set explicitly in `pgbackrest.conf` (and later, `psql -U restaurant_app`
   in the restore drill's own verification query, for the same reason).
3. **pgBackRest's S3 driver always speaks HTTPS**, with no plain-HTTP
   option (`repo1-storage-verify-tls` only skips certificate validation,
   not encryption) -- MinIO now runs with a self-signed TLS cert
   (`k8s/minio`'s `tls.secretName`) purely to satisfy this, since nothing
   else talks to MinIO.

Also: `--reuse-values` on a `helm upgrade` only reuses what the *previous*
release actually had -- a values.yaml key added after that release existed
(like `tls.secretName` above) comes back `nil`. `--reset-then-reuse-values`
is the fix (start from the chart's current defaults, then re-layer what was
explicitly set last time) -- both `harden-live-cluster.sh` upgrade calls use
it now.

## Restoring for real (a disaster, not a drill)

1. Stop every service that writes to TimescaleDB (the same list
   `harden-live-cluster.sh`'s step 7 restarts, scaled to 0 instead).
2. `kubectl exec timescaledb-0 -- pgbackrest --stanza=restaurant-platform restore`
   restores in place, into the real PGDATA -- only do this once the
   StatefulSet's pod has been scaled to 0 (`kubectl scale statefulset/timescaledb --replicas=0`),
   since pgBackRest needs the target directory not currently in use by a
   running Postgres.
3. Add `--target=` for point-in-time recovery to a specific moment instead
   of the latest available WAL; see `pgbackrest restore --help`.
4. Scale `timescaledb` back to 1 and let it start normally.
5. Restart the services from step 1.

## Changing the schedule or retention

Edit `values.yaml`'s `schedule.full` / `schedule.diff` (cron syntax) or
`repo.retentionFull` (how many full backups to keep; differentials expire
automatically once the full backup they depend on does), then
`helm upgrade timescaledb-backup k8s/timescaledb-backup -n kafka`.
