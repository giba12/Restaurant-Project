**What this project is, in one paragraph:** a simulated restaurant-operations data platform, built as a personal portfolio project, that ingests four kinds of synthetic sensor/POS/staffing events through a real MQTT→Kafka→storage pipeline, runs causal inference (not naive correlation) over that data (Phase 5), tracks live restaurant state in a digital twin, narrates findings through a strictly-scoped local LLM whose output is verified before it is stored (Phase 6), and serves a dashboard with an observability stack (Phase 7). Every "sensor" is fake; every piece of infrastructure processing it is real, free/open-source software, deployed to an actual local Kubernetes cluster. The point of the project is depth in AI integration, data engineering, IoT/AIoT patterns, Kubernetes, and digital-twin concepts — not depth in restaurant operations itself.

## 1. Project Purpose and Constraints

- **Type:** personal resume/portfolio project; secondary goal is commercial viability if a company shows interest.
- **Cost constraint:** every component must be free/open-source, or hand-built. No paid APIs, no licensed vendor tools, no paid container registries.
- **Contract-first constraint (hard requirement):** all simulated components (sensors, POS, vendor analytics) stand in for production integrations that don't exist yet. Every stand-in is built against a fixed, pre-committed schema so it can be swapped for a real integration later without touching downstream consumers. Schemas are committed before any producer/consumer code is written.
- **Learning goal priority, in order:** meaningful AI integration → data integration/analytics → IoT → AIoT → Kubernetes → digital twin. Depth over uniform shallow coverage.

## 2. Key Design Decisions and Rationale

| Decision | Rationale |
|---|---|
| **k3s over kind** | Persistence across sessions — stateful services (Kafka, TimescaleDB) require a cluster that survives reboots, not an ephemeral CI-style cluster. |
| **Causal inference engine (DoWhy + statsmodels) replacing naive plate-waste CV** | Original pitch (plate-waste camera → recipe-change recommendation) was causally weak — uneaten food does not equal dissatisfaction; portion size, to-go intent, and dietary restriction all confound it. CV plate-waste detection is also a solved, commercially saturated problem (Winnow, Metafoodx, Clean Plate Innovations), so building a competing model has no differentiation value. |
| **`PlateWasteEvent` schema explicitly models confounders** | To-go container use, dietary restrictions, and portion size variants are modeled as fields, not ignored. As of Phase 3, the simulator also encodes the causal relationship itself (see Section 3.3) — the field existing in the schema was necessary but not sufficient. |
| **LLM narrator strictly scoped to pre-computed findings** | The Ollama-based narrator never receives raw data and cannot originate a claim — it only phrases findings the causal engine has already established statistically. |
| **`source_kind` field (`simulated` / `vendor_integration`) in event schemas** | Enables future vendor adapter swaps without modifying downstream consumers. |
| **KRaft mode over ZooKeeper for Kafka** | Confirmed hard requirement, not a preference — the installed Strimzi operator (chart `strimzi-kafka-operator-1.2.0`) has removed ZooKeeper support entirely and exposes only KRaft-mode CRDs. |
| **Single combined controller+broker node pool** | Appropriate topology for local dev; avoids the overhead of separate controller/broker pools intended for production HA. |
| **Local Docker/Podman build + `k3s ctr images import`, no registry** | Strimzi's on-cluster build mechanism requires a container registry to push to — unnecessary overhead for a single-node local dev cluster with no paid/hosted services. |
| **Apache Camel Kafka Connector (`camel-mqtt-source-kafka-connector`) over Confluent's MQTT connector** | Apache 2.0 licensed. Confluent's MQTT connector carries a more restrictive community license, conflicting with the free/open-source constraint. |
| **One parameterized Docker image for all four simulators (Phase 3)** | A `SENSOR_TYPE` env var selects which Python module runs at container start, rather than building/tagging/importing four near-identical images. See Section 3.1. |
| **All `KafkaConnector` objects consolidated into one Helm chart (`kafka-connect-mqtt`) (Phase 3)** | Keeps every MQTT→Kafka topic bridge under single Helm ownership, avoiding the direct-`kubectl-apply`-vs-Helm ownership conflict already documented in item 14. |
| **TimescaleDB and MinIO deployed as hand-rolled StatefulSets, not wrapped third-party Helm charts (Phase 4)** | Both originally-planned dependency charts (`timescale/timescaledb-single`, Bitnami's `minio`) turned out to be built on abandoned or actively-destabilizing upstream distribution channels — see problem log items 26 and 30–32. Hand-rolling removes the dependency on third-party chart maintenance entirely and is arguably closer to this project's own stated Kubernetes-depth goal than chart assembly would have been. |
| **MinIO server image sourced from Chainguard (`cgr.dev/chainguard/minio`), not MinIO's own official image (Phase 4)** | MinIO stopped publishing free container images to Docker Hub/Quay.io as of 2025-10-23 (source-only distribution going forward). Chainguard publishes a free, continuously-updated, vulnerability-scanned build specifically filling this gap. See problem log item 32. |
| **Every hypertable carries a `raw_payload JSONB` column (Phase 4)** | Three of the four event schemas were not available in the session that authored the initial DDL; typed columns for those tables are inferred from prose documentation and explicitly marked as such. `raw_payload` guarantees no data loss if an inferred column is wrong, decoupling ingestion correctness from that gap. See Section 3.5. |
| **Storage consumer built on `python:3.11-slim`, not `3.12` (Phase 4)** | `kafka-python` 2.0.2 (the only actively-packaged pure-Python Kafka client available) has an unresolved compatibility bug with Python 3.12's import system in its vendored `six.moves` shim. 3.11 avoids the bug entirely; nothing else in the consumer depends on 3.12-specific behavior. See problem log item 35. |
| **`KafkaConsumer(..., api_version=(2, 8, 0))` explicitly pinned in `consumer.py` (Phase 4)** | `kafka-python` 2.0.2's automatic broker-version auto-detection (`check_version()`) fails unconditionally against this project's Kafka 4.3.1 broker (`NoBrokersAvailable`, reproduced 100% of the time despite a confirmed-healthy broker and open TCP path). Explicitly pinning a known-compatible protocol version bypasses the broken auto-detection path entirely rather than requiring a full client-library replacement. See problem log item 36. |

## 3. Architecture (Seven Layers)

1. Simulated MQTT edge device pods (one per sensor type: plate-waste camera, ticket timer, staffing sensor, POS terminal), non-uniform Poisson-process event rates.
2. Message backbone: Eclipse Mosquitto (MQTT) bridged into Apache Kafka via Strimzi Kafka Connect.
3. Storage: TimescaleDB (time-series) + MinIO (S3-compatible object storage). **Complete as of Phase 4 — see Section 3.5, 3.6.**
4. Causal & anomaly engine: anomaly detection (scikit-learn) first, then DoWhy/statsmodels causal inference with explicit confound modeling, paired with a scenario-injection controller.
5. Digital twin service: separate stateful microservice maintaining restaurant state as a graph/state machine — deliberately architecturally separate from the causal engine.
6. LLM narrator: local Ollama model, strict data-access boundary (structured findings only, never raw data).
7. Frontend: React dashboard (business-facing) + separate Prometheus/Grafana stack (platform observability).

### 3.1 Edge simulator design (Phase 3)

Each of the four simulators is a Python module (`edge-simulators/simulators/{plate_waste,pos_transaction,service_timing,staff_shift}.py`) exposing a `generate_event()` (or, for stateful sequences, a `next_event()` bound method) and a `main()`. All four run inside the **same** container image; which one runs is selected at Kubernetes Deployment level via a `SENSOR_TYPE` environment variable, read by a shared `entrypoint.py`.

Shared runtime (`edge-simulators/common/runtime.py`) is identical across all four and is responsible for loading the relevant JSON Schema once at startup, validating every generated event against that schema before publishing (fatal on violation — a code defect, not a skip-and-continue condition), publishing at a non-uniform Poisson-process rate, and distinguishing fatal (schema) errors from transient (MQTT connection) errors as two structurally different failure classes.

### 3.2 Shared world model

All four simulators import a single module, `edge-simulators/common/world.py`, defining the fixed domains they all draw from — one `restaurant_id`, fixed `station_id`/`table_id` lists, a ten-person `staff_id` roster, and a twelve-item menu. This join-key discipline is what makes the four independently-produced event streams joinable later, and now also what makes them meaningfully queryable together once persisted — see Section 3.5.

### 3.3 Confounder encoding is behavioral, not just structural

The `PlateWasteEvent` schema's `confounder_flags.to_go_container_used` field is wired into the generated waste value itself in the Phase 3 simulator — a to-go container reduces simulated `estimated_waste_grams` by roughly 75%. This matters for validating the Phase 5 causal engine: an engine correctly controlling for this confounder should recover a materially different effect estimate than one that ignores it.

### 3.4 Kafka topic bridge (Phase 3)

Four MQTT topics, one per simulator, each bridged by its own `KafkaConnector` instance on the `connect-cluster` Kafka Connect cluster. See Section 5 for the full topic/connector table (unchanged from the prior revision).

### 3.5 Storage schema and ingestion (Phase 4)

`storage/schema/001_hypertables.sql` defines four TimescaleDB hypertables, one per event type, applied via a Helm post-install/post-upgrade hook Job (`k8s/timescaledb/templates/schema-init-job.yaml`) rather than run manually — this keeps schema application reproducible and tied to the chart's own lifecycle rather than living as an out-of-band step in someone's shell history.

**Field-provenance caveat, carried forward from the session that authored the DDL:** the four committed `schemas/*.schema.json` files were not available in that session's context. `service_timing_events`' typed columns are confirmed directly against `edge-simulators/simulators/service_timing.py`'s actual event construction. The other three tables' typed columns (`plate_waste_events`, `pos_transaction_events`, `staff_shift_events`) were inferred from prose in this document and are marked `-- INFERRED` inline in the SQL. **This was subsequently corrected** — the person verified the SQL against the real schema files directly before deployment (see Section 7 for whether this correction has been re-confirmed against the version currently checked into the repo, since the corrected file was not re-reviewed in this document's authoring session). Every hypertable also carries a `raw_payload JSONB` column holding the complete original event regardless of which typed columns are populated, so an incorrect inferred column does not lose data.

The Kafka-to-TimescaleDB consumer (`storage/consumer/consumer.py`) subscribes to all four Phase 3 topics as a single process (mirroring the Phase 3 decision to use one parameterized image for four simulators, rather than four near-duplicate consumer deployments). It re-validates every event against the same JSON Schemas the edge simulators already validated against before publishing — treated as a distinct trust boundary, not redundant, since a future non-simulated producer (a real POS webhook adapter) would not have passed through the Phase 3 simulator's validation at all. Schema-violation failures are logged and skipped (non-fatal at this layer — see the consumer's module docstring for the reasoning, which differs from the edge simulators' fatal-on-violation policy deliberately). Database-write failures are retried with backoff and block offset commit, so a transient TimescaleDB outage cannot silently drop events.

### 3.6 TimescaleDB and MinIO: hand-rolled, not chart-wrapped (Phase 4)

Both storage components were originally planned as thin Helm charts wrapping third-party dependency charts (`timescale/timescaledb-single`, Bitnami's `minio`). Both dependencies turned out to be resting on distribution channels that failed or degraded during this same build session — see problem log items 26 and 30–33 for the full sequence. Both were rebuilt as hand-rolled `StatefulSet` + headless `Service` + `Secret` + init-`Job` manifests, pulling only the underlying container image directly:

- **TimescaleDB:** `timescale/timescaledb-ha:pg16-ts2.16-all` — still actively published; only the *chart* wrapping it was abandoned.
- **MinIO:** `cgr.dev/chainguard/minio` — MinIO's own image is no longer freely published at all as of 2025-10-23 (see item 32); Chainguard's build fills that gap.

Both charts generate their own dev-only credentials `Secret` from `values.yaml` by default (`credentials.create: true`), rather than requiring a pre-existing out-of-band Secret — this was itself the fix for problem log item 30.

## 6. Problems Encountered and Resolutions

Chronological; intended to prevent re-diagnosing the same issues. Items 1–25 (Phases 1–3) unchanged from the prior revision.

### Phase 4 additions (items 26–35)

26. **`helm dependency update k8s/timescaledb` failed: `can't get a valid version for 1 subchart(s): "timescaledb-single" ... version ">=0.35.0"`.** Root cause: the `timescale/helm-charts` GitHub repository was archived (unmaintained) in January 2024, with no releases since; the highest version ever published (`0.33.1`) does not satisfy the `>=0.35.0` constraint originally written. This was not a typo to fix — investigation confirmed the chart itself has no path forward. **Resolved by dropping the dependency-chart approach entirely** and hand-rolling a `StatefulSet` + `Service` + `Secret` + schema-init `Job` in `k8s/timescaledb/templates/`, pulling only the still-actively-published `timescale/timescaledb-ha` image directly, with no Helm chart dependency on Timescale's abandoned packaging. **General principle:** a pinned external chart dependency's *repository* can go stale independent of the *image* it deploys remaining current — `helm search repo <chart> --versions` (after `helm repo add`) is the direct way to confirm a chart repository is still actively maintained before depending on it further, rather than assuming a version constraint just needs adjusting.

27. **This document's own Section 5 stated the Helm chart convention as `k8s/charts/<service-name>/`, and this was wrong.** Verified during Phase 4 via `find . -maxdepth 4 -name 'Chart.yaml'` against the live repo — every existing chart (`k8s/timescaledb/`, `k8s/minio/`, `k8s/edge-simulators/`, etc.) lives directly under `k8s/`, with no `charts/` segment anywhere. The incorrect convention had been carried in this document since the Phase 3 revision without being re-checked against the actual repo state. **General principle, reinforcing item 22's original lesson from a new angle:** a written document describing a repo convention is not itself the source of truth — it can drift from the real repo silently across sessions, and should be spot-checked against the live filesystem (a one-line `find`) rather than trusted by default, especially before handing directory-path instructions to a person mid-task.

28. **A stray, fully-duplicated `timescaledb` chart was found nested inside `k8s/storage-consumer/`** (`k8s/storage-consumer/timescaledb/Chart.yaml`), alongside the correct, separate `k8s/timescaledb/` at the top level — almost certainly an artifact of a multi-directory `mv` during file reorganization landing one copy one level too deep. `diff -r` between the two confirmed byte-identical content before the stray nested copy was deleted. **General principle:** when a suspected duplicate is found, confirm via `diff -r` before deleting either copy — a clean diff makes deletion safe; a non-clean diff would mean determining which copy is authoritative first, a materially different and higher-stakes situation.

29. **`helm upgrade --install timescaledb k8s/timescaledb -n kafka` failed: `resource Job/kafka/timescaledb-schema-init not ready ... context deadline exceeded`.** This is a Helm hook **wait-timeout**, not a Job failure — `kubectl get jobs` showed the Job still genuinely `Running` (0/1), and `kubectl get pods` showed the `timescaledb-0` pod still `ContainerCreating` after 16+ minutes, consistent with a slow first-time pull of the `timescale/timescaledb-ha` image (a substantially larger image than anything pulled earlier in this project). This directly echoes problem log item 6 (Kafka broker reconciliation timeout caused by a slow cold image pull, not a real defect). **Resolved by waiting** — the pod reached `1/1 Running` on its own after roughly 20 minutes total, at which point the schema-init Job's `wait-for-postgres` initContainer unblocked and the Job completed without any Helm command needing to be re-run. **General principle, extending item 6:** a Helm hook timeout error should prompt the same `get → describe` check as any other apparent failure before assuming the underlying resource actually failed — Helm giving up waiting and the resource itself failing are different claims, and the StatefulSet/Secret/ConfigMap/Service from a failed-hook `helm upgrade --install` are typically already live regardless of the hook's own outcome.

30. **MinIO pod stuck in `ContainerCreating` for 175+ minutes** (well past the ~20-minute precedent from item 29, correctly recognized as no longer "just a slow pull") **— root cause `FailedMount`: `secret "minio-credentials" not found`.** This was a real gap in the originally-delivered chart, not an infrastructure issue: `k8s/minio/values.yaml` set `auth.existingSecret: minio-credentials`, but no template in that chart ever created a Secret by that name — unlike the `timescaledb` chart, which included its own `templates/secret.yaml` from the start. **Resolved in two steps:** (1) an immediate unblock via manually-created Secret (`kubectl create secret generic minio-credentials ...`), after first confirming the exact expected key names via `helm show values` (`auth.rootUserSecretKey` / `auth.rootPasswordSecretKey`, both blank by default — meaning the key names are caller-specified, not an implicit convention, and had to be set explicitly rather than assumed); (2) the proper fix, adding a `templates/secret.yaml` to the chart itself so credentials are chart-managed and reproducible rather than living only in shell history — mirroring the pattern already established for `timescaledb`. **Note:** the manually-created Secret had to be deleted (`kubectl delete secret`) before the chart's own Helm-managed version could be installed, to avoid the exact ownership-conflict class already documented in item 14.

35. **The storage-consumer pod, once the image reference was corrected, entered a genuine crash loop (`STATUS: Error`, restarting) — the first purely application-level (not scheduling/pull-level) failure of this Phase.** `kubectl logs` on the crashing pod showed a Python traceback bottoming out in `ModuleNotFoundError: No module named 'kafka.vendor.six.moves'`, raised from deep inside `kafka-python`'s own import chain (`kafka/codec.py` → `kafka/vendor/six.py`). Root cause, confirmed via direct research rather than assumption: `kafka-python` 2.0.2 (the version pinned in `storage/consumer/requirements.txt`) vendors an old copy of the `six` compatibility library using a `sys.modules`-registration technique that is incompatible with Python 3.12's import-system changes — a known, still-open upstream issue as of this session, with a fix planned for a future `2.0.3`/`2.1.0` release that had not shipped. 36. **The storage-consumer pod crash-looped 100% of the time with `kafka.errors.NoBrokersAvailable`, raised from inside `KafkaConsumer.__init__` → `check_version()`, despite a confirmed-healthy Kafka broker and a confirmed-open TCP path.** Diagnosed in stages, each ruling out one layer: (1) `kubectl get svc -n kafka | grep bootstrap` confirmed the actual bootstrap Service name (`restaurant-platform-kafka-kafka-bootstrap`, not the value originally guessed in `values.yaml`) — fixing this got DNS resolution working but did not fix the underlying error; (2) raw TCP reachability confirmed open via a disposable `busybox`/`nc` pod, ruling out network/Service-level causes; (3) the `Kafka` CR's listener spec confirmed `tls: false` with no `authentication:` block on the `plain` listener, ruling out an auth mismatch; (4) the broker's own logs, checked across the exact timestamps of every consumer crash, showed a completely healthy, unremarkable controller heartbeat with no errors — ruling out broker instability; (5) DEBUG-level consumer logging showed the socket connecting successfully, then a bare `Probing node bootstrap-0 broker version` with no further output before the exception — consistent with the broker responding to the version-probe request in a way `kafka-python` 2.0.2 cannot parse. Root cause, confirmed by elimination rather than a single definitive upstream source: `kafka-python` 2.0.2 (last released 2020) cannot complete its automatic API-version negotiation against a Kafka 4.3.1 broker — Kafka 4.0 made real protocol-level changes (ZooKeeper removal, dropped support for older inter-broker/client protocol versions) that this client predates. **Resolved by explicitly setting `api_version=(2, 8, 0)` on the `KafkaConsumer(...)` call**, bypassing the broken auto-detection path entirely rather than requiring a full client-library migration (e.g. to `confluent-kafka`) — confirmed working immediately: the very next log line after this change was a clean `Updating subscribed topics to: (...)`, the first time the consumer had ever gotten past its own constructor. **General principle:** a 100%-reproducible failure at the identical line, against a confirmed-healthy dependency, with no config explanation surviving elimination, points at a hard client/server version incompatibility — and for older, infrequently-updated client libraries specifically, an explicit protocol-version pin is a cheap thing to try before assuming a full library replacement is required.

37. **After item 36's fix, the consumer immediately hit a second, unrelated failure: `psycopg2.OperationalError: ... password authentication failed for user "$(DB_USER)"`** — note the literal, unsubstituted string `$(DB_USER)` in the error, not a real username. Root cause: Kubernetes' `$(VAR_NAME)` reference-substitution in container env values only resolves if `VAR_NAME` is defined **earlier** in the same container's `env:` list, top-to-bottom — it is not a whole-list name lookup. `k8s/storage-consumer/templates/deployment.yaml` defined `TIMESCALE_DSN` (which references `$(DB_USER)` and `$(DB_PASSWORD)`) *before* `DB_USER` and `DB_PASSWORD` themselves were defined later in the same list, so at the point Kubernetes evaluated `TIMESCALE_DSN`, those two variables did not yet exist for substitution purposes and were left as literal text. **Resolved by reordering the `env:` list** so `DB_USER`/`DB_PASSWORD` are defined before `TIMESCALE_DSN` references them — no other change needed. **General principle:** Kubernetes' `$(VAR)` env-value substitution is order-sensitive within a single container spec's `env:` list, unlike a typical shell environment where all variables in a given scope are simultaneously available regardless of declaration order — any env value that references another env value by `$(...)` must have that referenced variable declared strictly earlier in the same list.
