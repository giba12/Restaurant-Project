## 1. What this project is, and where Phase 5 fits

This is a personal portfolio project simulating a restaurant-operations data platform. Four kinds of synthetic events (plate waste, POS transactions, kitchen ticket timing, staff shifts) are generated by fake "sensors," published over MQTT, bridged into Kafka, and — since Phase 4 — persisted into TimescaleDB. Every "sensor" is fake; every piece of infrastructure processing the data is real, free/open-source software running on an actual local Kubernetes cluster (k3s, on WSL2/Ubuntu on a Windows machine).

Phase 5 is the **causal and anomaly engine**: it turns the raw event history Phase 4 made durable into (1) per-ticket derived summaries, (2) statistically-flagged anomalies, and (3) causal findings that control for confounders rather than reporting naive correlations. This is the layer the project's own design notes single out as the reason the plate-waste-camera pitch was rejected in the first place — see `restaurant-platform-project-notes.md`, "Prior critique that shaped the design."

**Phase 5's stated done condition** (from the project's own design notes): *an injected scenario produces a correctly attributed finding, not a raw correlation.* This has now been verified end-to-end — see the Status block above and Section 8.

## 5. Why things are built this way

- **`ticket_timing_summaries` is a plain table, not a hypertable.** Every other Phase 5 table (and every Phase 4 table) is an append-only event log, where TimescaleDB's time-partitioning helps. This table is the opposite — the aggregator upserts the *same row* repeatedly as a ticket progresses through stages, keyed by `ticket_id`, and is queried by `ticket_id`/`station_id`, not by time range. A hypertable would chunk-locate the row by its original insert time and gain nothing.
- **`causal-engine` has two entry points, not one.** The stream consumer is the production path. The one-shot CLI exists specifically because waiting for the anomaly detector to notice an injected scenario organically — with its 30-ticket-per-station cold-start requirement (`MIN_WINDOW_SIZE`) — is slow to exercise repeatedly during development. The CLI path writes the same `CausalFinding` shape, tagged with a real `scenario_injection_id`, so it can be checked against a scenario's known ground truth without waiting on the full pipeline.
- **`TREATMENT_MAP` is deliberately small (two entries) and hand-curated**, not a general framework. Per the module's own docstring, only the plate-waste entry (`to_go_container_used` → `estimated_waste_grams`) has "real backing data end-to-end" confirmed. The second (`staffing_level` → `pickup_delay_ms`) is explicitly flagged in-code as "a coarse proxy, not a validated causal variable." Don't add a third entry without first confirming the underlying columns exist and actually carry the claimed relationship — this is exactly the "contract-first" discipline `restaurant-platform-project-notes.md` establishes as a hard requirement, applied to a causal-engine query instead of a producer schema.
- **`anomaly-detector` runs two independent detection modes that can both fire on the same ticket.** This is intentional, not a bug to deduplicate — `AnomalyEvent.schema.json`'s `detection_method` field exists precisely so a downstream consumer can tell which method produced which finding.
- **Scenario injection is a Kafka control-plane topic, not direct Kubernetes-object mutation** (e.g., scaling a Deployment to 0). Rationale, from the controller's own docstring: a Kafka message is consumable identically whether the target is a simulated pod or a future real vendor integration; mutating Kubernetes objects would require this one microservice to hold RBAC permissions broader than its job needs; and a scenario needs an unambiguous start/end pair for the resulting finding to be attributable at all — a `start`/`end` message pair models that directly.
- **A `staffing_shortage` scenario models the effect via backlog growth, not per-station delay or a blocking sleep.** Removing a station from the assignable pool only changes which station new tickets land on; a ticket's own odds of being picked to advance are just `1/open_ticket_count`, independent of station. Two more direct-seeming approaches were tried and rejected: weighting ticket selection by station self-cancels once the population re-equalizes (only a transient effect, not sustained); an explicit `time.sleep()` would block the single-threaded simulator entirely, freezing *every* station, not just the affected ones. Letting the effective open-ticket cap grow (5x) during a shortage means more tickets genuinely compete for the same fixed tick budget for as long as the scenario lasts — a sustained, real slowdown, not a cosmetic one. See `service_timing.py`'s module-level comment for the full reasoning and bug #51.
- **The MQTT→Kafka source connectors are now committed to git as plain `KafkaConnector` YAML** (`k8s/kafka-connect-mqtt/connectors/`), where before they only existed as unmanaged cluster state (applied by hand in an earlier, undocumented session — see `k8s/kafka-connect-mqtt/`'s own chart, which only ever templated the `KafkaConnect` cluster itself, never the connectors). This matters for reproducibility: before today, tearing down and recreating this cluster from the committed repo alone would not have restored the MQTT bridge at all.

## 6. Constraints and design decisions worth understanding before touching this code

Project-wide constraints (cost, contract-first, learning-goal priority) are unchanged from Phase 1 — see `restaurant-platform-project-notes.md`. Phase-5-specific ones:

- **The `narrative_ready` gate on `CausalFinding` is never set `true` by anything built so far.** Every finding — from either causal-engine entry point — is written with `narrative_ready: false`. Flipping it is explicitly reserved for a separate human/automated review step, not yet built (this is Phase 6 territory). Don't treat a finding's mere existence as "safe to show a user."
- **Scenario injection only has a real effect on `service-timing` today, and only for `staffing_shortage`.** The controller's message schema accepts `target: "plate-waste" | "pos-transaction" | "staff-shift" | "all"` too, and will happily publish a message for any of them — but per the controller's own docstring, no consuming hook exists yet in those three simulators. A scenario targeting them is a silent no-op. `staffing_shortage` → `service-timing` (removing stations from the pool) is wired up **and confirmed working** (see Section 8) — but this took three separate fixes to actually reach that state (bugs #49–51), so don't assume a scenario type "exists" just because `SCENARIO_PARAM_SCHEMAS` accepts it. `order_volume_spike` is accepted by the controller too but has no consuming hook anywhere — same silent-no-op caveat applies.
- **`ticket-timing-aggregator`'s in-memory state does not survive a restart, by design** — but this had a sharper edge than intended (see bug #43). The current, fixed behavior: a ticket already mid-sequence when the pod (re)starts simply never gets a summary at all, rather than crashing the service. This is an accepted, documented gap, not a bug to "fix properly" without a real reason to add durable checkpointing.
- **All three Kafka consumer groups default to `auto_offset_reset="latest"`** (kafka-python's default, never overridden in this phase's code). A service's first-ever start will not backfill from whatever backlog already existed on its topic — only forward-looking data gets processed. This is why validating `causal-engine` today required the one-shot CLI path against historical rows already in TimescaleDB, rather than waiting on the live stream.
- **Each service loads its JSON Schema once, at startup** (`common.load_schema(...)` is called in `main()`, not per-message). A `phase5-schemas` ConfigMap update does not take effect in an already-running pod — you must `kubectl rollout restart` the affected deployments after any schema change. This bit us directly today (bug #45).
- **Python base image and Kafka client version pins carried over from Phase 4 apply here too**: `python:3.11-slim` (not 3.12 — `kafka-python`'s vendored `six` shim), `api_version=(2, 8, 0)` pinned on every Kafka client (auto-negotiation fails against this project's Kafka 4.3.1). See `linux-k8s-docker-helm-study-guide.md` Sections 6.3–6.4 for the original diagnosis; both pins are simply reused, not rediscovered, in all four Phase 5 Dockerfiles.

## 7. Bugs found and fixed (problem log items 38–51)

This project's `restaurant-platform-implementation-status.md` numbers its problem log 1–37 through Phase 4. Continuing that numbering here for consistency, even though this document lives separately.

**Found before anything was deployed (static review):**

38. **Wrong Kubernetes Secret name.** All three DB-writing charts' `values.yaml` set `pgPasswordSecretName: "timescaledb-app-credentials"`; the actual Secret (confirmed via `kubectl get secret -n kafka`) is `timescaledb-credentials`. Every affected pod would have failed with `CreateContainerConfigError` on first deploy. Fixed by correcting the value in all three `values.yaml` files.
39. **Missing `phase5-schemas` ConfigMap.** All three DB-writing deployments mount a ConfigMap literally named `phase5-schemas` for `/app/schemas`, but no chart anywhere created it. Fixed by writing a new chart, `k8s/phase5-schemas/`, whose only job is owning that one ConfigMap (via `Files.Glob`, so any `.json` file dropped into `k8s/phase5-schemas/files/` is picked up automatically).
40. **Missing `TicketTimingSummary.schema.json`.** The file existed in the sibling, stale top-level `restaurant-platform/schemas/` copy of this repo but not in the active `restaurant-platform-phase1/restaurant-platform/schemas/` directory the services actually build from. `ticket-timing-aggregator` would have crashed on its very first `common.load_schema(...)` call. Fixed by copying the file across.
41. **Schema/code drift on `ServiceTimingEvent`'s `stage` enum.** `service_timing.py` was mid-session updated to emit `order_fired`/`cook_started`/`plated`/`picked_up_by_server`/`delivered`, but the schema file in the same directory still had the old enum (`fired`/`started`/`plated`/`expo_hold`/`delivered`). Once rebuilt, the simulator would fail its own schema validation on every event (fail-loud by design — see `edge-simulators/common/runtime.py`) and crash-loop immediately. Fixed by updating the enum and description to match the code.
42. **`002_phase5_hypertables.sql` never wired into the DB schema-init Job.** `k8s/timescaledb/templates/schema-configmap.yaml` only ever embedded `001_hypertables.sql`; the Job's `psql` invocation only ever ran that one file. The three new Phase 5 tables would not have existed in the database. Fixed by adding a second `-f` argument to the Job and a second key to the ConfigMap.

**Found only by actually deploying and running it — none of these were visible from reading the code alone:**

43. **`ticket-timing-aggregator` crash loop from a real design gap, not the stage-name issue above.** The service's own docstring accepted that a ticket already mid-sequence when the pod (re)starts would have an unknown `order_time` — but `TicketTimingSummary.schema.json` requires `order_time` as a non-null string, so *any* such ticket produced a `jsonschema.ValidationError` and crashed the pod, which then immediately hit the same class of ticket again on restart. This was a guaranteed crash loop under normal operation, not a rare edge case. **Fixed in `aggregator.py`:** skip emitting a summary at all for a ticket whose `order_time` was never observed, instead of emitting an invalid one; still clean up the in-memory entry on `delivered` so it doesn't leak.
44. **The MQTT→Kafka bridge was silently broken for 3 of 4 real sensor topics.** `kubectl exec ... curl localhost:8083/connectors/<name>/status` showed `service-timing-source-connector`, `plate-waste-source-connector`, and `staff-shift-source-connector` all `FAILED` with `Client is not connected` (a Paho MQTT subscribe-time error), while `pos-transaction-source-connector` was healthy. Root cause: none of the five `KafkaConnector` objects set an explicit `camel.kamelet.mqtt-source.clientId`, and all five run inside the **same single Kafka Connect worker JVM** — without a unique ID, connectors implicitly share/collide on one, and each reconnect (of any of them) kicks whichever other connector currently holds it. This explains why the `service-timing-events` topic had only ~35 messages total despite 12 days of the simulator publishing at ~20/min — almost none of it was actually reaching Kafka. **Fixed** by patching a unique `clientId` onto all five connectors; all five went `RUNNING` within 20 seconds. **This was a pre-existing Phase 2/3 gap, unrelated to any Phase 5 code change** — it was only found because Phase 5 was the first time anyone actually needed `service-timing-events` to be flowing reliably in volume.
45. **`anomaly-detector` schema bug on `expected_range`.** `AnomalyEvent.schema.json` typed `expected_range` as strictly `"object"`, even though its own description says "Null/absent for isolation_forest" — and the detector's own `build_isolation_forest_event()` correctly sets it to `None` for that case, exactly as documented. The type declaration just never got the nullable treatment its sibling field (`anomaly_score`) already had. This crashed the pod the first time a real isolation-forest anomaly fired (confirmed: happened live, in production, about 50 minutes after deploy). **Fixed** by changing the type to `["object", "null"]`. Required restarting all three ConfigMap-consuming deployments afterward — see Section 6's note on schemas only loading once at startup.
46. **`storage-consumer` (Phase 4, unrelated to any Phase 5 code) had been silently discarding real data for as long as it's been running.** Discovered while trying to run `causal-engine`'s plate-waste analysis and finding `portion_size_variant` and the dietary-restriction confounder were **100% NULL across all 342 rows**. Two separate bugs in `storage/consumer/consumer.py`'s `insert_plate_waste`: `portion_size_variant` was read from `event.get("portion_size_variant")` (a top-level key that doesn't exist) instead of `confounders.get("portion_size_variant")` (it's nested inside `confounder_flags`, per `PlateWasteEvent.schema.json`); and the dietary flag was read via `confounders.get("dietary_restriction_flag")` — a key name that doesn't exist in the source event at all (the real key, per schema, is `declared_dietary_restriction`). A third, same-class bug was found in `insert_staff_shift`: `event.get("shift_event_type")` doesn't exist on `StaffShiftEvent` either — the real field is `shift_action`. **Fixed** the three `.get(...)` calls, then **backfilled 360 plate-waste rows and 170 staff-shift rows** directly from each row's already-correct `raw_payload` JSONB column (which had captured the true data all along — this is exactly the scenario `raw_payload` was added to guard against, per `phase4-handoff.md` Section 6). `causal-engine`'s `pickup_delay_ms` query was also fixed to match the real column name (`shift_event_type`, not `shift_action` — the DB column itself is misnamed relative to the schema, a separate, lower-priority naming-drift issue left as-is; see Section 9). **This bug predates Phase 5 entirely and had nothing to do with any Phase 5 code — it was invisible until Phase 5 tried to actually use the columns it silently corrupted.**
47. **Two unpinned transitive dependencies resolved to versions incompatible with the pinned direct dependencies.** `causal-engine/requirements.txt` pinned `statsmodels==0.14.2` and `dowhy==0.11.1` but left `scipy` and `networkx` unpinned. Pip resolved `scipy==1.17.1`, which removed a private function (`scipy._lib._util._lazywhere`) that `statsmodels` 0.14.2 imports — `ImportError` on startup. After pinning `scipy==1.13.1`, the next unpinned resolution (`networkx==3.6.1`) hit the same class of problem: `dowhy` 0.11.1's backdoor-set identification calls `networkx.algorithms.d_separated`, renamed in newer `networkx`. **Fixed** by pinning both (`scipy==1.13.1`, `networkx==3.2.1`).
48. **A `numpy.bool_` failed strict JSON Schema boolean validation.** `causal_engine.py`'s refutation-passed calculation (`abs(refutation.new_effect) < 0.25 * abs(estimate.value)`) produces `numpy.bool_`, not Python's native `bool` — `jsonschema` rejects it for a `"type": "boolean"` field even though it's truthy and behaves like a bool everywhere else in Python. This was the last failure standing between "computes a correct estimate" and "successfully writes a valid `CausalFinding`." **Fixed** with an explicit `bool(...)` coercion.

**Found while actually trying to close the done-condition loop — none of these were caught by the earlier deploy-and-verify pass, because that pass never actually tried to *use* scenario injection:**

49. **The scenario-injection feature was completely dormant.** `SCENARIO_CONTROL_ENABLED` — the env var that gates whether `service_timing.py` even constructs its scenario-control consumer thread — was never set anywhere in `k8s/edge-simulators/`'s chart. The feature existed in code, wired correctly, and would never once have activated in the deployed cluster. **Fixed** by adding `scenarioControlEnabled: true` to the chart's `values.yaml`, templated as an env var applied uniformly to all four simulators (harmless for the three that don't read it).
50. **Even with the flag on, the pod would have crashed immediately.** `edge-simulators/requirements.txt` never listed `kafka-python` at all — `service_timing.py`'s deferred `from kafka import KafkaConsumer` import (deliberately deferred so the other three simulators, and this one when scenario control is off, don't need the dependency) would have raised `ModuleNotFoundError` the moment `SCENARIO_CONTROL_ENABLED=true` actually took the code down that path. Worse, `edge-simulators/Dockerfile` was still on `python:3.12-slim` — the exact combination (`kafka-python` 2.0.2 + Python 3.12) already known from Phase 4 (problem log item 35) to fail with `ModuleNotFoundError: No module named 'kafka.vendor.six.moves'`. **Fixed** by adding `kafka-python==2.0.2` to requirements and switching the base image to `python:3.11-slim`, matching every other Kafka-consuming image in this project.
51. **Even fully enabled, a `staffing_shortage` scenario was causally inert.** Removing a station from `_available_stations()` only changes which station *new* tickets get assigned to — it has zero effect on any individual ticket's `pickup_delay_ms`/`cook_duration_ms`, since those are wall-clock gaps between real event timestamps, and a ticket's odds of being picked to advance on any tick are simply `1/len(open_tickets)`, independent of station. No amount of waiting would ever have produced a detectable anomaly from this mechanism as originally written. Two fixes were tried and rejected before finding the right one — both are documented in `service_timing.py`'s module-level comment and in Section 5 above — before landing on: raise the effective open-ticket cap 5x during an active shortage, so backlog genuinely grows at the stations absorbing the load, sustainedly (not transiently) lowering each ticket's real pick frequency. **Fixed and empirically confirmed**: a real 10-minute scenario run produced a mean `pickup_delay_ms` increase from ~31.6s (baseline) to ~105s (during) at the three affected stations, a DoWhy-estimated effect of **+73,851ms controlling for station, with refutation passed** — see Section 8 for the full run.

## 8. How to verify this is actually working, yourself

Don't trust `kubectl get pods` showing `Running` alone. Run this sequence:

```bash
# 1. Pod stability across all four Phase 5 services
kubectl get pods -n kafka -l 'app in (causal-engine,anomaly-detector,ticket-timing-aggregator,scenario-injection-controller)'

# 2. Are all five MQTT source connectors actually healthy (not just RUNNING at the connector level)?
```

## 9. Known open items

Ordered roughly by how much they matter before Phase 6 depends on this layer:

1. **The pipeline's own live-fired `pickup_delay_ms → staffing_level` findings (Section 8, step 9) are mechanically correct but not substantively meaningful.** They passed refutation and the loop fired exactly as designed — but `staffing_level` is computed from real `staff_shift_events` clock-ins, a data stream the scenario-injection mechanism never touches. Treat those three specific findings as proof the *pipeline* works, not as evidence about *this specific scenario's* real cause — that proof is the separate targeted analysis in Section 8. Don't add a `stations_removed`-aware treatment to `TREATMENT_MAP` without deciding how the live anomaly stream would actually supply that context (it currently only carries `window_start`/`window_end`/`metric_name`/`station_id`, not which scenario, if any, was active).
2. **[Resolved 2026-09-20: `insert_plate_waste` and `insert_pos_transaction` were corrected against the real schemas.]** **`pos_transaction_events` has the same class of bug as items in #46, but wasn't fixed.** `storage-consumer`'s `insert_pos_transaction` assumes one `menu_item_id`/`quantity`/`unit_price` per transaction, reading them from top-level event keys — but `POSTransactionEvent.schema.json` defines `line_items` as an array (one transaction can have several), with the real per-item fields named `unit_price_cents` (not `unit_price`) and the staff field named `server_staff_id` (not `staff_id`) at the top level. All four columns are currently always NULL. No Phase 5 component reads this table today, so it wasn't fixed as a side effect of this work — but it needs an actual design decision (approximate with the first line item, or add a proper child table) before anything depends on it.
3. ~~`dietary_restriction_flag` (the DB column name) doesn't match `declared_dietary_restriction`~~ **Resolved 2026-09-17**, alongside the Phase 7/portability work: `storage/schema/001_hypertables.sql` was independently corrected (by someone/something outside this session, discovered while testing the portability path against a fresh database) to rename both this column and `staff_shift_events.shift_event_type` (→ `shift_action`) to match their canonical schema names. `storage/consumer/consumer.py` and `causal_engine.py` were updated to match, and the live k3s database was migrated in place (`ALTER TABLE ... RENAME COLUMN`) so both environments agree. Found via real testing, not inspection: a fresh Docker Compose database build from the current schema file immediately surfaced both mismatches as "column does not exist" errors, since the k3s database had been running on the pre-rename schema the whole time and never noticed.
4. **[Resolved in Phase 6: the `finding-reviewer` service flips it.]** **`narrative_ready` has no reviewer step yet.** Every finding sits at `false` forever until Phase 6 builds something to flip it.
5. **`plate-waste`, `pos-transaction`, and `staff-shift` scenario-injection targets are accepted but are silent no-ops** — only `service-timing` has a consuming hook. Worth deciding whether Phase 6's narrator work needs any of these before adding them.
6. **[Resolved in Phases 6 and 7: all four charts are implemented.]** **The digital-twin, LLM-narrator, dashboard, and observability chart skeletons remain untouched** — the same caveat `phase4-handoff.md` already raised for Phase 4, still true now.

## 10. What comes next

Phase 6: the digital twin and LLM narrator. The narrator's hard constraint — it may only ever read `causal_findings`, never raw event data or `anomaly_events` directly — is already encoded in `CausalFinding.schema.json`'s own description, so Phase 6 has a contract to build against. The full detect-and-attribute loop is now verified end-to-end (Section 8), so Phase 6 can trust that `causal_findings` rows get produced automatically from real conditions — but keep item 1 above in mind: not every row in that table has been checked against a known ground truth the way this session's `staffing_shortage` run was. A finding sitting in the table having passed refutation is a weaker claim than "we deliberately caused this and got the right answer."
