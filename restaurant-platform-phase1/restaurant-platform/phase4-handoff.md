# Phase 4 Hand-Off: Storage Layer

**Audience:** someone with no prior exposure to this codebase. This document is self-contained — it doesn't assume you've read any prior chat history, only that you can read the referenced files if you want more depth than what's summarized here.

**Status: Phase 4 is complete and verified**, as of the most recent session. "Verified" means: data is flowing end-to-end from the simulated sensors through Kafka into TimescaleDB with zero loss, zero schema violations, and zero consumer lag — not just "the pods are running."

---

## 1. What this project is, and where Phase 4 fits

This is a personal portfolio project simulating a restaurant-operations data platform. Four kinds of synthetic events (plate waste, POS transactions, kitchen ticket timing, staff shifts) are generated by fake "sensors," published over MQTT, bridged into Kafka, and — as of Phase 4 — persisted into a real time-series database. Every "sensor" is fake; every piece of infrastructure processing the data is real, free/open-source software running on an actual local Kubernetes cluster (k3s, on WSL2/Ubuntu on a Windows machine).

The project is built in seven phases. Phase 4 is the **storage layer**: it takes the event stream that Phases 1–3 already built (schemas, message backbone, edge simulators) and makes it durable and queryable. Before Phase 4, data existed only transiently in Kafka. After Phase 4, it's sitting in a real database, ready for Phase 5's causal-inference engine to query.

**Phase 4's stated done condition** (from the project's own design notes): historical data is queryable directly, independent of any dashboard. This is now true.

## 2. What was actually built

Three components, each with application source at the repo root and a Helm chart under `k8s/`:

| Component | Source | Chart | What it does |
|---|---|---|---|
| TimescaleDB | `storage/schema/001_hypertables.sql` | `k8s/timescaledb/` | Postgres + the TimescaleDB extension. Four hypertables, one per event type. |
| MinIO | *(no app source — off-the-shelf image)* | `k8s/minio/` | S3-compatible object storage. Currently holds one empty placeholder bucket; nothing writes to it yet (see Section 6). |
| Storage consumer | `storage/consumer/consumer.py` | `k8s/storage-consumer/` | A Python process that reads all four Kafka topics and writes each event into its matching TimescaleDB table. |

None of these three are wrapped third-party Helm charts — each is a **hand-written** `StatefulSet` (or `Deployment`, for the consumer) plus a `Service`, a `Secret`, and — for TimescaleDB and MinIO — an init `Job` that runs once on install to set up schema/buckets. This wasn't the original plan; see Section 5 for why.

## 3. How data actually flows, end to end

```
edge-sim-plate-waste, edge-sim-pos-transaction,        (Phase 3, unchanged)
edge-sim-service-timing, edge-sim-staff-shift pods
        │  publish over MQTT
        ▼
   Mosquitto  →  Kafka Connect (Camel MQTT connector)  →  Kafka topics    (Phase 2/3, unchanged)
        │
        ▼
   storage-consumer pod                                                   (Phase 4, new)
        │  1. re-validates each event against schemas/*.schema.json
        │  2. writes to TimescaleDB (raw_payload JSONB always;
        │     typed columns where the schema mapping is confirmed)
        ▼
   TimescaleDB (4 hypertables)                                            (Phase 4, new)
```

The consumer is a **single process** subscribed to all four topics at once (not four separate consumer deployments) — this mirrors a decision already made in Phase 3, where all four simulators share one container image, parameterized rather than duplicated.

**Why the consumer re-validates events that the edge simulators already validated before publishing:** these are treated as two different trust boundaries. The edge simulators are simulators — but the schemas are written so a *real* vendor integration (a real POS webhook, say) could eventually replace a simulator without any downstream code changing. A real integration would never have passed through the Phase 3 simulator's own validation step, so the consumer can't assume upstream validation already happened.

## 5. Why hand-rolled Kubernetes manifests instead of off-the-shelf Helm charts

This wasn't the original design. Both TimescaleDB and MinIO were originally planned as thin wrapper charts around well-known third-party Helm charts (`timescale/timescaledb-single` and Bitnami's `minio`, respectively). Both fell apart during the actual build, for different reasons:

- **TimescaleDB's chart repository is abandoned.** `timescale/helm-charts` on GitHub has been archived since January 2024, with no releases past `0.33.1`. The underlying database image is still fine and actively published — only the *Helm packaging around it* had stopped being maintained.
- **MinIO hit two separate, unrelated distribution failures in quick succession.** First, Bitnami stopped publishing free versioned image tags to Docker Hub in August 2025 (moving them to a frozen, explicitly-unmaintained `bitnamilegacy` repository) — this broke both MinIO's console and its actual server image. Then, when the plan shifted to pulling MinIO's *own* official image directly instead of Bitnami's repackaging, that turned out to be blocked too: MinIO's project stopped publishing free container images entirely in October 2025. The resolution was a third party's free image (Chainguard's `cgr.dev/chainguard/minio`), built specifically to fill that gap.

**The fix, in both cases, was the same:** stop depending on someone else's chart, and write a `StatefulSet` + `Service` + `Secret` (+ an init `Job` where needed) directly, pulling only the underlying container image. This trades more manifest-writing work for zero dependency on third-party chart maintenance — and, arguably, is a better demonstration of the Kubernetes skills this project exists to showcase in the first place.

## 6. Design decisions worth understanding before touching this code

- **Every hypertable has a `raw_payload JSONB` column, in addition to typed columns.** The typed columns for three of the four tables (`plate_waste_events`, `pos_transaction_events`, `staff_shift_events`) were originally *inferred* from prose documentation, because the real schema files weren't available in the session that first wrote the SQL. `raw_payload` guarantees the complete, correct event is always stored regardless of whether a typed column turned out to be named or typed wrong. **This has since been hand-corrected against the real schemas by the project owner, but that correction has not been independently re-reviewed** — treat the typed columns for those three tables with mild caution until someone checks them side-by-side against `schemas/*.schema.json` again.
- **`service_timing_events`' typed columns, by contrast, are fully confirmed** — taken directly from `service_timing.py`'s own event-construction code, not inferred.
- **MinIO holds one empty placeholder bucket (`plate-waste-images`) and nothing else.** No component in this project currently produces blob/image data — MinIO is deployed now purely to establish the storage contract ahead of a possible future computer-vision stretch goal, which is explicitly out of scope for the core project.
- **The storage-consumer's Python base image is pinned to 3.11, not 3.12.** `kafka-python` (the Kafka client library in use) has an unresolved bug on 3.12 involving its bundled `six` compatibility shim.
- **The consumer explicitly pins `api_version=(2, 8, 0)` on its Kafka client.** Without this, `kafka-python`'s automatic broker-version detection fails 100% of the time against this project's Kafka version (4.3.1) — the library is old (last real release in 2020) and predates some protocol changes in newer Kafka. The pin sidesteps the broken auto-detection path entirely.
- **Credentials for both TimescaleDB and MinIO are dev-only placeholders, generated automatically by each chart.** Fine for a single-user local cluster that nothing outside the machine can reach. Would need to be replaced with real secret management before any broader deployment.

## 7. Hard-won operational lessons (skip this section if you just want to know current state, come back if something breaks)

A few of these are specific enough to this exact stack that they're worth knowing before you start debugging from scratch:

- **Podman silently prefixes locally-built image names with `localhost/`.** If a chart's `values.yaml` references `local/my-image:1.0` instead of `localhost/local/my-image:1.0`, Kubernetes will fail to find the locally-cached image and instead attempt (and fail) a real Docker Hub pull. Always confirm an image's actual stored name via `sudo k3s ctr images ls` rather than assuming it matches whatever you passed to `-t`.
- **A Helm post-install hook timing out (`context deadline exceeded`) does not mean the underlying resource failed.** It means Helm's own wait window (5 minutes by default) elapsed before the hooked Job reported success — often because a large image (like TimescaleDB's) is still on its first, slow pull. Check `kubectl get pods`/`kubectl get jobs` directly before assuming anything actually broke; a second `helm upgrade --install` while the first is still legitimately in progress just restarts the same race.
- **Minimal/distroless container images (Chainguard's, in this project) often have no shell at all in their default tag.** A `command: [sh, -c, "..."]` container spec against one of these fails immediately with `exec: "sh": executable file not found in $PATH` and empty logs. These images typically have a separate `-dev` tag with a full userspace for exactly this situation.
- **Kubernetes' `$(VAR)` substitution inside an env value only works if that variable is declared *earlier* in the same container's `env:` list.** Unlike a shell, order matters. A DB connection string referencing `$(DB_USER)` before `DB_USER` is itself declared will literally pass the string `$(DB_USER)` as the username — the tell is an auth error where the "username" in the error message is obviously a template placeholder, not a real value.

## 8. How to verify this is actually working, yourself

Don't trust `kubectl get pods` showing `Running` alone — that only confirms Kubernetes' own health probes are passing, not that data is actually moving. Run this sequence:

```bash
# 1. Pod stability — restart count should not be climbing
kubectl get pods -n kafka -l app.kubernetes.io/name=storage-consumer

# 2. Row counts across all four tables
kubectl exec -n kafka timescaledb-0 -it -- psql -U restaurant_app -d restaurant_platform -c "
SELECT 'plate_waste' AS t, count(*) FROM plate_waste_events
UNION ALL SELECT 'pos_transaction', count(*) FROM pos_transaction_events
UNION ALL SELECT 'service_timing', count(*) FROM service_timing_events
UNION ALL SELECT 'staff_shift', count(*) FROM staff_shift_events;"

# 3. Zero silently-dropped events
kubectl logs -n kafka -l app.kubernetes.io/name=storage-consumer | grep -c "SCHEMA VIOLATION"

# 4. The strongest signal: Kafka's own accounting of what's been consumed
kubectl exec -n kafka restaurant-platform-kafka-dev-pool-0 -it -- \
  /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group storage-consumer
```

Check #4's `LAG` column is `0` and `CURRENT-OFFSET` equals `LOG-END-OFFSET`, on every topic-partition, and that those numbers match check #2's row counts exactly. That three-way match — Kafka's committed offset, Kafka's actual log length, and the database's row count — is the real confirmation that every message ever published has been consumed, validated, and persisted with nothing lost and nothing outstanding.

## 9. Known open items (small, non-blocking, but real)

- **Re-verify the three tables' inferred columns against the real schema files, side by side, one more time.** See Section 6. Not urgent — data isn't being lost either way, thanks to `raw_payload` — but worth closing before Phase 5 queries those typed columns directly.
- **A stage-enum question in `service_timing_events` that resolved itself without a clear explanation.** An earlier analysis flagged that `service_timing.py`'s code (as last reviewed) emits stage names that shouldn't pass this table's `CHECK` constraint at all — yet live data shows every message being accepted with zero violations. The likely explanation is that the simulator's actual deployed code has already been fixed since that code was last reviewed, but this hasn't been directly confirmed. A one-line query settles it: `SELECT DISTINCT stage FROM service_timing_events;` — if it only returns the schema's current enum values, this is a non-issue.
- **MinIO is pinned to Chainguard's `:latest` tag**, since no free versioned tag is available from that source. A future `helm upgrade` on that chart could silently pull a different build than what's running today. Not a problem yet, since nothing depends on MinIO's specific version behavior currently.
